# f4 issue #926 — Win32 GUI fallback fonts

## Задача

Исправить отображение символов из `languages_most_complex_2.txt` в `f4-gui`
на Windows при установленном шрифте, когда терминальные backend'ы уже показывают
эти символы корректно.

## Что установлено по логам

- Проблема воспроизводится в backend `win32` (`BACKEND: GDI SetDIBitsToDevice`),
  терминальный путь работает.
- В логе сборки `f17d6cf` (до GDI-фикса) на `languages_most_complex_2.txt` есть
  ровно одна строка discovery — `U+0710` → `seguisym.ttf`, probe и drop. Для
  Odia, Devanagari, Bengali, Tamil и остальных индийских письменностей нет ни
  одной строки. Discovery логирует каждый существующий кандидат, значит на той
  машине не нашлось ни одного файла из курируемой таблицы имён (`Nirmala.ttf`,
  `kalinga.ttf` и прочих) — при том что те же символы рисует терминал.
  То есть исходная причина — поиск файла шрифта, а не растеризация.
- Прогретая coverage-битмапа пропускает `seguisym.ttf` для `U+0710` без probe:
  в cmap Segoe UI Symbol этого символа нет.

## Что было сделано и откачено

Коммиты `8dd3d8b` и `539e8cc` добавляли Windows-only растеризацию через GDI
`GetGlyphOutlineW` для glyphs, которые `x/image` «знает, но не умеет рисовать».
GDI отвечает и на символы, которых в выбранном шрифте нет (`.notdef` или
подстановка font linking), поэтому обёрнутый шрифт начинал «уметь» всё:
в сборке `464b5f1` `U+12A0` и `U+0B13` резолвятся в `seguisym.ttf` вместо
`ebrima.ttf` и цепочка останавливается на нём, а `warm()` вырос с 15.3 мс до
931 мс для `seguisym.ttf` и с 8.1 мс до 3.24 с для `segoeui.ttf`. Изменение
откачено; посылка, ради которой оно писалось, логами не подтверждается.

## Текущее решение

Там, где нет fontconfig (Windows, macOS), discovery после курируемых имён
спрашивает систему о том, что реально установлено: файлы шрифтов из
font-директорий и, на Windows, ключ реестра
`SOFTWARE\Microsoft\Windows NT\CurrentVersion\Fonts` (HKLM и HKCU) — там
записаны и per-user шрифты, и пакеты optional features, лежащие вне
`%SystemRoot%\Fonts`. Покрытие читается из cmap через `opentype.ParseReaderAt`,
то есть probe читает нужные таблицы, а не файл целиком.

## Чего пока не знаем

Почему именно курируемые имена не нашлись на машине репортёра: шрифты лежат
вне просмотренных директорий или названы иначе. Обе ветки закрываются опросом
системы, а новые строки лога отвечают на вопрос прямо:

- `FONT_INVENTORY: N installed font files: ... directories, ... registry`
- `FONT_INVENTORY: probed N of M installed fonts for U+XXXX in ...: K carry it`
- `GUI_FONT: no font renders U+XXXX (script), N fonts consulted`

Раньше «шрифт не найден» и «найден, но отброшен» оставляли в логе одинаковую
тишину.
